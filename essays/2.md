When I first started programming, I never really thought about there being a correct way to ask a programming question. Usually my questions were something like "Why did you implement this?", "What is the point of this?", or the classic "Why doesn't this work?" If I was stuck, my main goal was just to find somebody who knew more than me and hopefully get an answer. After reading Eric Raymond's *How to Ask Questions the Smart Way*, I started to realize that asking for help is a skill of its own. In software engineering, where I like to think coding is 10% writing code and 90% figuring out why that code does not work, being able to communicate a problem clearly can make debugging significantly easier.

Raymond argues that programmers should do some investigation themselves before asking for help and then provide useful information when they finally ask. That means describing the problem, showing what they tried, including relevant error messages, and being clear about what they are trying to accomplish. Looking through Stack Overflow showed me what happens on both sides of this idea. A good question makes it easy for someone else to start debugging with you. A bad question makes the person helping you figure out what your question even is before they can do anything else.

## A Smart ROS 2 Question

One example I found was a Stack Overflow question titled "Using 'docker exec' to run ros2 commands." [Using "docker exec" to run ros2 commands, Stack Overflow](https://stackoverflow.com/questions/74114225/using-docker-exec-to-run-ros2-commands?utm_source=chatgpt.com)

The developer was trying to write a shell script that would execute ROS 2 commands inside a Docker container. Instead of simply writing "ROS 2 doesn't work in Docker, help," they showed exactly what they were trying to accomplish. More importantly, they included multiple commands they had already tried.

For example, they tried running `ros2 node list` through `docker exec`, sourcing their `.bashrc`, running the command through another shell script, and calling the ROS 2 installation directly. Each attempt was followed by its actual error message, things like `ros2: not found` or `ros2: command not found`.

That matters because the error message immediately narrows down the problem. Someone reading the question does not have to wonder whether the ROS 2 node crashed, Docker failed to start, networking stopped working, or the command just produced the wrong output. They know right away that the shell cannot find ROS 2.

Because of that, the response was short and direct. The answer explained that the ROS installation was most likely not being sourced properly inside the container and suggested explicitly sourcing `/opt/ros/humble/setup.bash` before running `ros2 node list`.

What I like about this example is how little back and forth was necessary. The person answering did not need to start with ten questions asking what operating system was being used, what command was run, or what the terminal printed. Most of the diagnostic information was already sitting right there in the post.

That lines up with one of Raymond's main points, which is to be precise and informative about the problem. He recommends describing the symptoms, the environment, the research already done, and any diagnostic steps already taken. The Stack Overflow question does exactly that.

It also relates to something I have learned on my own, which is that error messages are extremely useful. Copying an error message might feel like a small detail, but it can turn "something is broken" into a much smaller set of possible problems.

## When the Question Becomes the Problem

For comparison, I found a Stack Overflow question titled "Why ' ' doesn't work? 'expected expression, empty character constant'." [Why ' ' doesn't work?, Stack Overflow](https://stackoverflow.com/questions/66866389/why-doesnt-work-expected-expression-empty-character-constant?utm_source=chatgpt.com)

The developer included a short C program with a `display()` function and tried passing an empty character literal into it. But the post gives almost no explanation outside of the source code itself. There is no description of what the complete program is supposed to produce, no explanation of what the programmer already tried, and very little context around the mistake. The title mostly just repeats the compiler error instead of turning it into an actual technical question.

The outcome ended up being almost the opposite of the ROS 2 example. Stack Overflow closed the question because it needed details or clarity, meaning it was no longer accepting answers in its current form.

Even though source code was provided, source code by itself is not automatically a good question. The person answering still has to figure out what the programmer actually intended the code to do. A better version of this post would explain the expected output, include the exact compiler error, point to the problematic line, and explain what had already been tried.

This is exactly what Raymond warns against with code questions. Dumping a huge chunk of code and saying it does not work is much less useful than isolating the problem and explaining what was expected versus what actually happened.

Another thing that bothers me about questions like this is the assumption that somebody else will just spend their own time figuring everything out. If it's clear the person asking has not tried anything themselves, I am a lot less interested in helping. I would guess experienced developers on Stack Overflow feel the same way.

## I Have Been on the Other Side

Unfortunately, I have learned this lesson the hard way too.

While working on my university rover team, I had written a ROS package that worked fine on my laptop but would not work correctly on any of the other team members' computers. Specifically, a certain node would only pop up when I ran it on my machine and never showed up for anyone else. Everything ran, nothing crashed on my end, but nobody could figure out why it only behaved that way for me. I eventually asked some of my leads for help. The real problem was that I did not understand my own implementation well enough to explain what was actually different about my setup.

That created a pretty frustrating situation. They were trying to help me figure out why that node only showed up for me and not them, but I couldn't clearly explain how the package worked or why I had built certain parts of it the way I did. We basically got stuck, because I could show them that it worked on my laptop without being able to give them enough information to explain why it didn't work anywhere else.

In the end, we never actually figured out the root cause. My laptop ended up going with the rover all the way to competition in Utah, simply because it was the one machine where that node actually showed up.

Looking back, the technical problem was only part of the issue. The communication problem made the technical problem so much harder than it needed to be. If I had understood my own code well enough to describe the environment, the dependencies, the behavior, and the differences between all of our computers, we would have had a much better starting point for actually solving it instead of just working around it.

## One Part of the Advice I Question

I agree with most of Raymond's technical advice, but I don't fully agree with how harsh he is toward new programmers.

New programmers are going to ask bad questions sometimes because they don't know enough yet to realize why their question is bad in the first place. Telling somebody to research their problem before asking is fair. Treating every poorly written question as pure laziness is not.

This feels especially relevant now that AI tools exist. A beginner doesn't need to be thrown straight into an unforgiving technical community just to learn how to ask better questions. They can ask an AI assistant first, get more patient feedback, figure out what information they're missing, and eventually turn a vague question into something an actual developer can answer.

So I still think Raymond's principles hold up, even though the environment around programming has changed a lot since he wrote that essay. The goal shouldn't be to punish someone for asking a bad question. It should be to help them learn how to turn it into a good one.

## Don't End With "Never Mind, I Fixed It"

The part of Raymond's essay that stuck with me the most was actually what he says should happen after the problem gets solved.

Raymond recommends following up with a brief explanation of the actual fix, so the people who helped you, and anyone who finds the thread later, know what actually worked.

I've searched for programming problems before, found someone describing almost the exact issue I was having, and then gotten to the end of the thread only to see something like:

> Never mind, figured it out.

That has to be one of the most frustrating ways a thread can end.

The original poster got the benefit of the whole discussion, but the next programmer who stumbles on that thread gets basically nothing out of it. Even one sentence explaining what fixed the problem could turn an old, half finished conversation into something genuinely useful for the next person.

## Communication Is Part of Engineering

The biggest thing I took away from all of this is that communication isn't separate from software engineering. It is software engineering.

Knowing how to write code is obviously important, but eventually that code is going to break, interact badly with someone else's code, behave differently on another machine, or throw an error you've never seen before. At that point, being able to clearly explain what you expected, what actually happened, and what you already tried matters just as much as writing the original code did.

A smart question doesn't guarantee a solution, and a badly written question doesn't mean the person asking it is a bad programmer. But asking a clear question removes a lot of unnecessary work from the debugging process. The easier I make it for someone else to understand my problem, the easier it becomes for them to actually help me solve it.

Sometimes the bug really is in the code. Other times, the first thing that needs debugging is the question itself, or honestly, the person sitting in front of the screen typing it.
